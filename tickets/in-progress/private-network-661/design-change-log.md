# Design Change Log: private-network-661

DC IDs continue extensions-ui-516's (DC-001…DC-090) so every change to the Private Network and Manage Nodes design has one ID.

| ID | Kind | Change | Why / IDs |
| --- | --- | --- | --- |
| DC-091 | Removal | The Private Network page offers Tailscale only: no network choice (Headscale, Host a private network), no "Your own VPN" section, no Invite someone. Join reads "Join your private network" with Sign in with Tailscale and "Use an auth key instead". The card description names only Tailscale and says "Needs no administrator password" (was "approval", which collided with Tailscale's device approval). This node's "own VPN" mode is gone. | D-1, REQ-001, REQ-002; non-goals |
| DC-092 | Changed | Tailscale's conditions are separate states, each an amber notice on the page and the card's status line: Waiting for approval (kept); **Your Tailscale sign-in expired** (key expiry, Sign in again); **Signed out of Tailscale** (signed out or removed in the admin console, Sign in again); **Tailscale can't be reached** (trying again by itself, no button). Signed out and expired hide My machines (this machine is not on the network). Manage Nodes → This node shows the same line with Open Private Network. | REQ-015 |
| DC-093 | Addition | Access rules: "Your tailnet's access rules block AutoByteus." notice naming the machines, "Blocked by access rules" (amber) in My machines' State column; the card stays On with the status line saying it. | REQ-017 |
| DC-094 | Addition | Pair again: every pairing made before the update keeps its row (Controlled nodes or Paired nodes) with an amber "Paired before the update" mark and **Pair again** in the Pair column. Controlled node: one click → Pairing… → Paired. Someone else's node: Pair again → "Waiting for its owner to accept" + Cancel → Paired (Teammate · peer only). A controlled node on an older AutoByteus: Pair again disabled, "{name} runs an older AutoByteus. Update it, then pair again." next to its existing Update button. | D-3, REQ-012, UC-010, AC-011 |
| DC-095 | Addition | Pair by address: a "Pair with someone else's node" band at the top of Paired nodes (Address, Pair; hint "Its owner accepts on that node. Pairing never gives control of either node."). The asking node shows a row with the address: "Waiting for its owner to accept" + Cancel → Paired; or "Its owner declined." + Pair again + remove. Errors: format, this node, a controlled node ("pair it with Pair on its row"), already paired, no AutoByteus node answers, an older AutoByteus. Paired nodes' empty text shortened to "No paired nodes of other people yet." | D-5, REQ-008, UC-006, AC-007 |
| DC-096 | Changed | Asking to pair shows requests that arrive by address even without the private network: "{name} at {address} wants to pair" with Accept / Reject; no account line. A node paired by address shows "Teammate · peer only" and no "Private network" tag; its Unpair text: "…to work together again, one of you pairs by address again." | D-5, REQ-008 |
| DC-097 | Addition | Add a node: a pasted access code whose address is on the private network (100.64.0.0/10, fd7a:115c:a1e0::/48) while this computer's node is not on it shows an amber notice "This access code is for a node on your private network ({address}). This computer's node must join your private network first." with Set up / Open Private Network; Add node is disabled. | REQ-010, G1 |
| DC-098 | Changed | Found: a machine shared from another tailnet reads "shared by {account}", or "shared with you" when Tailscale does not report the account; then "Someone else's node: pairs as a teammate when its owner accepts…" and "Waiting for its owner to accept". The teammate line no longer repeats the account: "{account}'s node: pairs as a teammate when they accept, never with control". | REQ-016 |
| DC-099 | Changed | Leave this private network: "{machine} signs out of your tailnet. Its pairings over the private network stop working. After it joins again, pair those nodes again." (a rejoined machine has a new machine ID, pairing-contract §1, §5); while signed out, expired or unreachable: "It stays listed in your Tailscale admin console until you remove it there." | pairing-contract §1, §5 |
| DC-100 | Changed | The join-first notice (DC-097) applies wherever an access code is pasted: Add a node (a box under the form), a Needs connecting row and Found → Control (one inline line with the link, inside the row's existing amber notice; Connect / Add disabled). | Solution Designer, F-3 → REQ-010 |
| DC-101 | Changed | Pair by address: no "older AutoByteus" error (DESIGN.md rule 9: no version checks on someone else's node). A node that does not accept the request: "{address} did not accept the pair request. Check that it runs the latest AutoByteus." beside "No AutoByteus node answers at …". The version note stays only on a controlled node's row (DC-094), which knows the version through the node-update connection. | Solution Designer, F-4 |
| DC-102 | Changed | Consistency with the node-key model (Solution Designer's capture check): a paired node runs this version, so the paired docker example is current (0.1.0) outside the after-update state; after the update it is older, with Update offered and Pair again disabled. A teammate's node paired before the update has no trash icon: its old pairing stays with Pair again until it is paired again (Remove means giving up control, which this app never had). Expired / signed-out captures retaken with My machines hidden (DC-092); Found → Control example uses raspberrypi's own code. | Solution Designer, round 1 check |
| DC-103 | Addition | This node → **Local network**: "Visible on my local network", off by default, shown with or without Private Network (DNS-SD, no extension). Help: "Other AutoByteus nodes on this local network see this node's name and address and can ask to pair with it. Nothing outside this network sees it." While on: "Visible as {name} at {address}". Turning it on while this node does not accept connections from this local network (the existing per-network setting of Phone Setup) shows "Accept connections from this network?" with "Allow and make visible" / Cancel. | D-6, REQ-018, UC-012 |
| DC-104 | Addition | **Found on your local network**, its own section after Found on your private network. Rows "{name} at {address}", no "added by" (no accounts); Control (the node's access code, with the "You did not add this node" warning; no join-first, the code carries a local address) and Pair (pair by address: "Waiting for its owner to accept" + Cancel → Paired nodes "Teammate · peer only"; "Its owner declined" + Pair again). Look again. Empty: "No AutoByteus nodes visible on this network. A colleague's node appears here when they turn on Visible on my local network. Some office Wi-Fi blocks this: then type its address under Pair with someone else's node." The other node sees "{name} at {address} wants to pair" (DC-096). | D-6, REQ-018, REQ-019, AC-013 |
| DC-105 | Decision | Both networks on: two separate Found sections, not one tagged list. Each has its own lead and empty state and its own trust context (accounts and "added by" vs. none), and each appears on its own (local without Tailscale, Tailscale without the local network). A node found on both appears once, under Found on your private network (it knows "added by"). | D-6, contract §4b |
